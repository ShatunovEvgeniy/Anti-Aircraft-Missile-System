# Варианты внедрения ЭПР и уравнения радиолокации

## Цель

Добавить в симулятор:

- коэффициент отражающей поверхности цели (ЭПР, `sigma`, м^2);
- расчёт обнаружения не только по геометрии, но и по радиолокационной формуле;
- архитектуру, которую можно развивать без переписывания основной логики радара.

Сейчас в проекте обнаружение работает так:

- цель должна находиться в секторе обзора;
- цель должна быть в пределах `max_range`;
- при выполнении этих условий цель считается обнаруженной.

Это простая геометрическая модель. ЭПР и энергетика сигнала пока не учитываются.

## Базовая формула

Для моностатической РЛС в упрощённом виде:

```text
Pr = Pt * G^2 * lambda^2 * sigma / ((4pi)^3 * R^4 * L)
```

где:

- `Pr` - мощность принятого сигнала;
- `Pt` - мощность передатчика;
- `G` - коэффициент усиления антенны;
- `lambda` - длина волны;
- `sigma` - ЭПР цели;
- `R` - дальность до цели;
- `L` - суммарные потери.

Условие обнаружения:

```text
Pr >= Pmin
```

Отсюда максимальная дальность обнаружения:

```text
Rmax = ((Pt * G^2 * lambda^2 * sigma) / ((4pi)^3 * Pmin * L))^(1/4)
```

Ключевое следствие:

```text
Rmax ~ sigma^(1/4)
```

То есть дальность зависит от ЭПР по четвёртой степени корня. Это удобно для упрощённых моделей.

## Вариант 1. Калиброванная модель по опорной ЭПР

### Идея

Использовать текущую дальность радара как паспортную дальность для цели с опорной ЭПР.

Формула:

```text
Rdetect(sigma) = Rref * (sigma / sigma_ref)^(1/4)
```

где:

- `Rref` - известная дальность радара для опорной цели;
- `sigma_ref` - опорная ЭПР, например `1.0 м^2`;
- `sigma` - ЭПР конкретной цели.

### Что нужно добавить

В цель:

- `radar_cross_section_m2`

В радар:

- `reference_rcs_m2`
- трактовку текущего `max_range` как `Rref`

В логику обнаружения:

- проверку `distance <= Rdetect(sigma)` вместо `distance <= max_range`

### Плюсы

- минимальные изменения в архитектуре;
- математически согласовано с базовым уравнением радиолокации;
- просто объяснить пользователю;
- удобно калибровать по справочным данным;
- легко добавить в текущий GUI.

### Минусы

- это не полная физическая модель;
- разные РЛС будут различаться в основном только опорной дальностью;
- не учитываются частота, шумы, потери, режимы обработки;
- обнаружение остаётся бинарным.

### Когда подходит

- для текущего симулятора как первый этап;
- если нужен реалистичный эффект ЭПР без перегрузки интерфейса.

## Вариант 2. Полное уравнение радиолокации в явном виде

### Идея

Хранить основные энергетические параметры РЛС и рассчитывать дальность обнаружения напрямую по формуле.

Пример параметров радара:

- `transmit_power_w`
- `antenna_gain`
- `frequency_hz` или `wavelength_m`
- `system_losses`
- `min_detectable_power_w`

У цели:

- `radar_cross_section_m2`

### Возможная формула

```text
Rmax = ((Pt * G^2 * lambda^2 * sigma) / ((4pi)^3 * Pmin * L))^(1/4)
```

или через порог по SNR и шумовую модель, если развивать дальше.

### Плюсы

- физически наиболее корректный вариант из детерминированных;
- можно моделировать разные типы РЛС содержательно, а не только через одну дальность;
- хорошая база для дальнейшего расширения;
- проще обосновывать результаты с инженерной точки зрения.

### Минусы

- сильно усложняет параметры радара;
- потребует аккуратной калибровки всех величин;
- сложнее UI и сохранение сцен;
- пользователю труднее задавать реалистичные числа;
- без шумовой модели результат всё равно будет частично идеализирован.

### Когда подходит

- если цель проекта ближе к инженерному тренажёру;
- если важна сопоставимость разных РЛС по физическим параметрам.

## Вариант 3. Нормированная энергетическая модель без абсолютных единиц

### Идея

Не использовать реальные `Pt`, `G`, `Pmin`, а хранить у радара один агрегированный коэффициент чувствительности.

Пример:

```text
detect_score = radar_power_factor * sigma / R^4
```

Обнаружение:

```text
detect_score >= threshold
```

Или эквивалентно:

```text
Rdetect = (K * sigma)^(1/4)
```

### Плюсы

- проще, чем полная физика;
- сохраняет правильную зависимость `1 / R^4`;
- удобен для игровых и учебных симуляторов;
- можно тонко калибровать поведение без жесткой привязки к справочным данным.

### Минусы

- хуже интерпретируется в реальных единицах;
- требует собственных условных коэффициентов;
- сложнее объяснять, чем вариант с `Rref` и `sigma_ref`;
- есть риск превратить модель в набор эмпирических чисел.

### Когда подходит

- если реализм важен, но абсолютная физическая достоверность не критична;
- если нужно быстро управлять балансом модели.

## Вариант 4. Вероятностное обнаружение поверх радиолокационной формулы

### Идея

Сначала вычислять энергетическую достижимость цели, затем получать не бинарный результат, а вероятность обнаружения.

Примеры:

- через отношение текущей дальности к `Rmax`;
- через SNR;
- через таблицу или аппроксимацию `Pd(SNR, Pfa)`.

Вместо логики "обнаружена / не обнаружена" получается:

- далеко от предела обнаружения: высокая вероятность;
- вблизи предела: нестабильное обнаружение;
- за пределом: практически нулевая вероятность.

### Плюсы

- поведение радара выглядит заметно живее;
- хорошо сочетается с уже существующими ошибками измерения;
- ближе к реальной задаче обнаружения слабых целей;
- можно моделировать срывы захвата и пропуски отметок.

### Минусы

- сложнее тестировать;
- результаты становятся недетерминированными, если не зафиксировать генератор;
- возрастает сложность объяснения пользователю;
- это уже не только геометрия и не только энергетика, а ещё и статистика.

### Когда подходит

- как второй этап после внедрения детерминированной модели;
- если нужна более реалистичная динамика сопровождения.

## Вариант 5. Разделение на этапы: обнаружение, захват, сопровождение

### Идея

Не использовать одну и ту же формулу для всех режимов радара.

Разделить:

- дальность первичного обнаружения;
- дальность устойчивого захвата;
- условия сопровождения;
- качество измерения координат.

Пример:

- первичное обнаружение требует более сильного сигнала;
- сопровождение возможно дальше или стабильнее после захвата;
- ошибка измерения зависит от мощности отражённого сигнала.

### Плюсы

- ближе к реальному поведению РЛС;
- хорошо сочетается с уже имеющейся логикой сканирования и tracking;
- даёт основу для более правдоподобного поведения ракетного комплекса.

### Минусы

- заметно усложняет модель и код;
- требует проектировать состояние радара аккуратнее;
- без хороших параметров может стать трудно предсказуемым.

### Когда подходит

- после базового внедрения ЭПР;
- если планируется развитие симулятора в сторону тактической модели.

## Рекомендуемый путь внедрения

### Этап 1

Взять вариант 1.

Минимальный набор:

- добавить `radar_cross_section_m2` в `Trajectory`;
- добавить `reference_rcs_m2` в `Radar`;
- считать допустимую дальность как:

```text
Rdetect = max_range * (sigma / reference_rcs_m2)^(1/4)
```

- вынести проверку из `contains_point(...)` в методы, которые принимают и цель, и её позицию.

Почему это лучший старт:

- почти не ломает существующую архитектуру;
- использует правильную зависимость по ЭПР;
- позволяет быстро получить заметный эффект в симуляции;
- оставляет путь к полной формуле.

### Этап 2

Если потребуется больше физики, перейти к варианту 2 или 3:

- либо хранить реальные параметры РЛС;
- либо ввести агрегированный коэффициент чувствительности.

### Этап 3

Если нужна более реалистичная динамика:

- добавить вероятностное обнаружение;
- разделить обнаружение, захват и сопровождение.

## Рекомендуемые изменения в архитектуре

Сейчас `Radar` часто получает только `point`. Для ЭПР этого недостаточно, потому что дальность обнаружения зависит от самой цели.

Поэтому лучше перейти от API вида:

```python
contains_point(point, t)
can_track_point(point)
```

к API вида:

```python
contains_target(target, point, t)
can_track_target(target, point)
get_detection_range_for_target(target)
```

Это позволит:

- учитывать ЭПР без хаков;
- позже учитывать тип цели, помехи и режим сопровождения;
- не размазывать радиолокационную логику по `gui.py`.

## Практические значения по умолчанию

Если брать вариант 1, можно стартовать так:

- `reference_rcs_m2 = 1.0`
- типовая цель: `3.0 .. 5.0 м^2`
- крупная цель: `10.0 .. 20.0 м^2`
- малозаметная цель: `0.1 .. 0.3 м^2`
- БПЛА: `0.01 .. 0.5 м^2`

Важно: эти значения зависят от ракурса, диапазона частот и режима полёта. Для симулятора их лучше считать приближёнными.

## Вывод

Наиболее рациональный путь для текущего проекта:

1. Сначала внедрить вариант 1 как калиброванную модель по опорной ЭПР.
2. Сразу перестроить API радара так, чтобы он принимал объект цели, а не только точку.
3. После этого решать, нужен ли переход к полной энергетической модели и вероятностному обнаружению.

Этот путь даёт хороший баланс между инженерной корректностью, сложностью кода и удобством настройки.
